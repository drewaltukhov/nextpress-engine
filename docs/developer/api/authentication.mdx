---
title: Authentication
description: How to authenticate API requests with Bearer tokens.
---

Every request to `/api/v1/*` must include a valid Bearer token in the `Authorization` header.

## Making authenticated requests

```bash
curl -H "Authorization: Bearer npp_your_token_here" \
  https://your-site.com/api/v1/me
```

## Authentication flow

When your request arrives, NextPress runs a 6-step validation:

1. **Extract token** from the `Authorization: Bearer <token>` header
2. **Hash and lookup** — compute SHA-256 of the token, query `api_tokens` table
3. **Check the owner** — the token's owner must be an active, not-deleted user who still holds the **administrator** role. Only administrators can create tokens, so a demoted or disabled owner's tokens stop working on the next request (restoring the role restores them).
4. **Check expiration** — verify the token hasn't passed its `expires_at` date
5. **Verify scope** — confirm the token has the scope required by the endpoint
6. **Check IP allowlist** — if the token has `allowed_origins`, verify the request IP matches a CIDR range

If any step fails, you get a `401` or `403` with an error code explaining what went wrong.

## Session vs. token auth

NextPress uses two authentication systems:

| | Session (admin UI) | Bearer token (API) |
|--|---|---|
| **Where** | `/admin/*` routes | `/api/v1/*` routes |
| **Mechanism** | NextAuth JWT cookie | `Authorization: Bearer` header |
| **Identity** | Logged-in user | Token owner (a user) |
| **Permissions** | Full user role | Token scopes (owner must be an active administrator) |
| **Rate limiting** | No | Yes (per-token bucket) |

## Token-acts-as-user model

Every token belongs to an administrator (only administrators can create one), and the token's **scopes** narrow what it may do. For example, a token with only `posts:read` can read posts but cannot change them, even though its owner could. If the owner stops being an active administrator, every token they own is rejected with `401` until the role is restored.
